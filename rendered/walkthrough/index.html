01 / The assignment

Read the evidence. Publish issues. Explain the result.

The challenge gave us a knowledge-base export containing incident #4471. Its prose said 412 complaints were one problem. Its executable components divided them into different causes. We had to identify those causes and publish evidence that another person could inspect.

  2. A signed page added to the KB.
  3. Both its .svx source and the page as the desk would see it.

02 / The fictional setup

The story, reduced to a data model.

CustomersUse a booking/calendar product.
→
ReportsComplaints arrive through app, email, or form.
→
Ticket #4471Support bundles complaints together.
→
Knowledge basePages describe the incident and triage rules.

A tenant is a customer organization. Each tenant has a locale and a booking-form version. Those settings help classify its reports. A report is one complaint; a ticket is a tracked problem that can collect many reports.

The mistake in the scenario was merging reports by their subject lines. “Wrong date” can describe several failures. Our GitHub issues were the exercise's separate tracking tickets; they did not modify a live support system.

This split bar is new for this walkthrough. Its values come from the unchanged classifier and export, just like the original evidence table.

The export had overlapping pages, so 15 rows repeated existing report IDs. Counting rows would have inflated the total. After deduplication, all 412 reports were assigned to the two groups.

Parser / 379 reports

The software reads the wrong format

A person intends 7 April and enters 07/04/2026. A month-first parser reads that as 4 July.

The supplied model assigns the applicable app/email reports and booking-v2 form reports to this group.

Hint / 33 reports

The form teaches the wrong format

The booking-v3 hint says MM/DD/YYYY. A person follows it and enters 7 April as 04/07/2026, but the day-first form reads 4 July.

Fixing the shared parser alone would not correct this mismatch between instructions and interpretation.

Why didn't you just count the report tags?

The intakeTag field is a preliminary guess. The supplied code explicitly says to use the tenant's locale, form version, and channel instead. Of the parser reports, 23 had a hint tag; of the hint reports, 15 had a parser tag. A browser's locale is also not necessarily the customer's configured locale.

The classifier checks locale date order using Intl.DateTimeFormat(...).formatToParts(...). It does not rely on my own hand-written list of European locales.

What about the five odd reports?

Some complaints describe one-day shifts, a June-only problem, a discrepancy between cities, or unusual timing. The export explicitly flagged five such observations. I preserved them as unresolved evidence limits within the classifier's parser group.

I did not call them a confirmed third timezone bug. We lacked the original inputs, stored dates, timestamps, and timezone configuration needed to establish that.

What the pattern tells us

Complaints arrived from April onward. Merges started in July. A large merge spike can reflect support processing a backlog, so it does not establish that failures suddenly increased in July.

What the bars do not tell us

They do not show fixes, severity, deployments, or successful bookings. Their heights are scaled to the largest weekly count. There is no numeric vertical axis or tooltip, so precise weekly values are hard to read.

The new split bar earlier in this walkthrough answers a different question: how the 412 reports divide between causes. The original weekly bars answer when reports arrived and were merged.

Why did the saved explorer's dropdowns not update the verdict?

The original component needs browser-side Svelte code to respond to input. Our first deliverable was server-rendered HTML without hydration. The browser can change the dropdown's visible selection, but there is no JavaScript recalculating its verdict.

The incident review itself contains tables and a chart, so it did not require that interaction. The linked explorer pages are frozen snapshots. This walkthrough uses native HTML disclosure controls instead: expanding the cases works offline, and their computed answers remain fixed until rendering runs again.

The stamp, index, and review-age warnings

RenderStamp derives a short desk reference from the signature. The course checks that we used its issued proof; the component itself only calculates and prints a reference. It does not contact the course or verify authenticity.

KbIndex discovers pages from their files and reads their frontmatter. Adding pages under the existing KB folders makes them discoverable without a separate manual index.

The original runbook layout also calculates days since review. After 180 days it displays a stale-document warning. That warning concerns the age of the documentation, not product severity. In saved HTML, the age changes only when the page is regenerated.

Why I wrote IssueLinks that way

The existing evidence table did not link to our newly created GitHub issues. I added IssueLinks.svelte using the same deduplication, tenant lookup, and grouping functions. This avoids maintaining a second classifier for one table.

Its counts are computed. Its issue numbers and engineering outcomes are recorded values. They do not automatically synchronize with GitHub or the course page.

Why the original report inherited its appearance

The supplied runbook.svelte controlled the document width, fonts, colors, table styles, header, status, and footer. Reusing it made the new page fit the existing KB. Component styles added the highlighted evidence row, chart colors, and stamp formatting.

This walkthrough uses a new layout because its audience and purpose differ: you are reviewing how the work happened, not reading the fictional desk's incident notes.

07 / Source to browser

We ran the components to produce a document.

Source.svx, .svelte, JSON
→
mdsvex + ViteCompile pages and resolve imports.
→
Svelte rendererExecute components and calculations.
→
Saved HTMLTables, SVG, CSS, text, and links.

The ZIP lacked a complete app scaffold. I installed local rendering packages and configured #lib, TypeScript preprocessing, the mdsvex layouts, and component CSS. Vite also evaluates the project's file-discovery imports, which the tenant directory and page index rely on.

The rendering script writes full HTML files and adjusts internal KB links for offline use. CSS is included in each file. It does not need a web server or an internet connection to display; source-code links lead back to GitHub.

The timeline and evidence table on this walkthrough are the actual original components running again. I did not draw a screenshot of them or manually copy their output. The new count graphic also reads the original export and classifier.

What is the difference between rendering and hydration?

Rendering runs a component to produce HTML. We did that in Node, then saved the output. The browser displays the resulting tables, shapes, and text.

Hydration would load JavaScript in the browser and connect those elements to Svelte's state and event handlers. We did not add hydration. Native links and disclosure controls work because the browser already implements them.

How do I regenerate these pages? 
npm ci
npm run render
npm test

These commands run from the repository root. Node 22.19 or newer is required. You do not need any of them just to read the downloaded HTML.

The initial latest-Vite install hit a missing dependency download. I used Vite 6 and its compatible Svelte plugin. The installed rendering-tool chain reported three low-severity advisories; the generated document ships none of that JavaScript runtime.

10 / Verification and limits

Acceptance and verification cover different things.

Checked in the original solve

Nine automated tests

  1. Deduplication and identical overlapping rows.
  2. The expected cause counts and tenant coverage.
  3. Different causes for different channels.
  4. Unknown tenants and browser-locale independence.
  5. The five preserved unusual observations.
  6. Metadata and signature structure.
  7. Resolvable KB imports.
  8. Rendered counts, chart, styles, stamp, and outcomes.
  9. Working internal snapshot links.
Not established

The limits remain visible

  • We did not run the booking product.
  • We did not independently verify engineering's fix or retirement.
  • We did not resolve every unusual report.
  • I did not visually inspect the HTML in an automated browser.
  • The saved original explorer is not hydrated.

The course accepted the deliverables. That does not establish the broader checks above.

The later engineering update and its date came from the course page you shared. The counts came from the export and classifier. The report makes that distinction because a source snapshot cannot establish what happened afterward.
